# Інструкція — РозкладкаВ (від А до Я)

Повний гід: де що лежить, як зібрати, як запустити, як вносити зміни та
синхронізувати між Windows і WSL.

## 1. Структура: дві копії проєкту

Проєкт живе у **двох незалежних копіях**, обидві — окремі git-клони одного
репозиторію `https://github.com/lubomyrfalfushynskyi/rozkladka_v`:

- **WSL (Linux)** — `~/rozkladka_v` (тобто `/home/franco/rozkladka_v`).
  Тут працює Claude Code, тут зроблено початкову розробку.
- **Windows** — `C:\Users\Admin\Desktop\rozkladka_v`. Тут відкривається
  Android Studio, тут можна клацати застосунок на емуляторі/телефоні.

⚠️ **Це не спільна папка** — зміни в одній копії НЕ з'являються автоматично
в іншій. Синхронізація йде через git: закомітив і запушив в одній копії →
підтягнув (`git pull`) у другій. Якщо редагуєш код в Android Studio на
Windows — не забудь запушити, інакше Claude Code у WSL цього не побачить,
і навпаки.

## 2. Встановлене середовище

### WSL
- Flutter SDK: `~/development/flutter`
- Android SDK: `~/Android/sdk`
- JDK 21 (Temurin, portable): `~/development/jdk/jdk-21.0.12+8`
- Усе прописано в `~/.bashrc` (`PATH`, `ANDROID_HOME`, `JAVA_HOME`)

### Windows
- Android Studio: стандартна інсталяція (містить власний JDK, але ми
  використовуємо окремий Temurin JDK — стабільніше для командного рядка)
- Flutter SDK: `C:\dev\flutter`
- Android SDK: `C:\Users\Admin\AppData\Local\Android\Sdk`
- JDK 21 (Temurin): `C:\Program Files\Eclipse Adoptium\jdk-21.0.11.10-hotspot`
- Змінні середовища (`JAVA_HOME`, `ANDROID_HOME`, `PATH`) прописані постійно
  на рівні користувача — новий термінал підхоплює автоматично, Android
  Studio теж (після перезапуску, якщо змінні мінялись після її старту)
- AVD-емулятор **Pixel_API_34** (Android 14, x86_64) вже створено

## 3. Як відкрити проєкт в Android Studio (Windows)

1. Відкрий Android Studio
2. **File → Open** → обери `C:\Users\Admin\Desktop\rozkladka_v`
3. Дочекайся синхронізації Gradle (перший раз може зайняти хвилину-дві)
4. Угорі, біля кнопки ▶ Run, обери пристрій:
   - **Pixel API 34** — емулятор (Device Manager праворуч → ▶ навпроти AVD)
   - або підключений по USB телефон з увімкненим USB-налагодженням
     (з'явиться в тому ж списку пристроїв)
5. Натисни ▶ **Run** — застосунок збереться і встановиться на обраний пристрій

## 4. Типові проблеми з емулятором (і як їх лікувати)

**"Running multiple emulators with the same AVD"** — вже є завислий процес
емулятора з тим самим AVD. Закрий усі вікна емулятора, у Диспетчері завдань
зверни `qemu-system-x86_64.exe`/`emulator.exe`, якщо лишились — і запусти
заново.

**Емулятор запускається, але не з'являється в списку пристроїв (adb)** —
перезапусти adb-сервер:
```powershell
adb kill-server
adb start-server
adb devices
```

**Емулятор довго не стартує / чорний екран** — на ноутбуках з гібридною
графікою (дискретна + інтегрована відеокарта) буває конфлікт із
Vulkan-рендерингом. Запусти емулятор вручну з програмним рендерингом:
```powershell
cd C:\Users\Admin\AppData\Local\Android\Sdk\emulator
.\emulator.exe -avd Pixel_API_34 -gpu swiftshader_indirect
```

**Помилка збірки після `flutter pub upgrade`** (jni / "v1 embedding" /
compileSdk-конфлікт) — пакети `file_picker`, `share_plus`,
`path_provider_android` мають історію несумісностей одне з одним і з нашою
версією Flutter/AGP. У `pubspec.yaml` є `dependency_overrides` для
`path_provider_android` (2.2.23 — новіші тягнуть пакет `jni`, який не
збирається) і `flutter_plugin_android_lifecycle`, а в
`android/build.gradle.kts` — примусовий `compileSdk 36` для всіх
підпроєктів (бо `file_picker` хардкодить 34 у власному build.gradle). Якщо
після оновлення пакетів збірка знову падає — спочатку перевір, чи не
змінились ці версії, перш ніж копати глибше.

## 5. Запуск і збірка з командного рядка (Windows PowerShell)

```powershell
cd C:\Users\Admin\Desktop\rozkladka_v

# Запустити на вже відкритому пристрої/емуляторі (з hot reload):
flutter run

# Зібрати debug APK (для швидкого тестування):
flutter build apk --debug

# Зібрати release APK (менший розмір, для реальної установки):
flutter build apk --release
```

Готові APK з'являються в:
`build\app\outputs\flutter-apk\app-debug.apk` (або `app-release.apk`)

## 6. Запуск і збірка з командного рядка (WSL)

```bash
cd ~/rozkladka_v
flutter build apk --debug      # або --release
flutter test                    # прогнати тести
flutter analyze                 # статичний аналіз
```

APK з'являється так само в `build/app/outputs/flutter-apk/`.

⚠️ У WSL немає підключеного emulator/телефона за замовчуванням — це
середовище для розробки й перевірки коду (тести, аналіз, компіляція), не
для інтерактивного клацання застосунком. Для клацання — Windows-копія.

## 7. Встановити готовий APK на реальний телефон

1. На телефоні: **Налаштування → Про телефон** → 7 разів тапнути "Номер
   збірки", щоб увімкнути режим розробника
2. **Налаштування → Для розробників** → увімкнути "Налагодження USB"
3. Підключити телефон по USB до Windows-ноутбука, підтвердити на телефоні
   запит на дозвіл налагодження
4. Скопіювати `app-release.apk` на телефон (через USB-провідник, хмару,
   Telegram "Збережені повідомлення" тощо) і встановити напряму — Android
   попросить дозволити "встановлення з невідомих джерел", погодитись
5. Або, якщо телефон підключений і видно в `adb devices`:
   ```powershell
   adb install -r app-release.apk
   ```

## 8. Як вносити зміни в код

1. Редагуй файли в `lib/` (екрани — `lib/screens/`, логіка розрахунку —
   `lib/services/calculation_service.dart`, моделі даних — `lib/models/`)
2. Якщо застосунок вже запущений через **Run** в Android Studio — просто
   збережи файл і натисни ⚡ (Hot Reload) або 🔄 (Hot Restart) — зміни
   з'являться без повної переустановки
3. Перевір, що нічого не зламалось:
   ```bash
   flutter analyze
   flutter test
   ```
4. Закомить і запуш зміни (з тієї копії, де редагував):
   ```bash
   git add -A
   git commit -m "Опис зміни"
   git push origin main
   ```
5. У другій копії (WSL чи Windows) підтягни зміни:
   ```bash
   git pull origin main
   ```

## 9. Git — базові правила проєкту

- Одна гілка — **main**, прямі коміти, без feature-гілок/PR (одна людина
  на проєкті)
- Ніяких згадок ШІ в комітах/коді
- APK-файли (`build/`, `*.apk` в корені) навмисно **не** комітяться в git —
  це бінарні файли, що легко перезібрати командою вище; тримати їх в
  історії git — зайве роздування репозиторію

## 10. Облік реальних вогнегасників і недостача

З версії 2.0 застосунок не лише рахує норму, а й веде облік фактично
наявних вогнегасників та показує різницю (недостачу).

**У кожного вогнегасника:**
- **Ідентифікатор (№)** — порядковий номер, присвоюється автоматично при
  додаванні (ніколи не повторюється, навіть після видалення)
- **Заводський номер** — вписується вручну (написаний на самому вогнегаснику)
- **Інвентарний номер** — лише цифри, мінімум 4 (перші 4 — код субрахунку
  бухобліку за типовою кореспонденцією, решта — порядковий номер у ньому)
- **Тип** — один з чотирьох: ВП, ВВК (заряд у кг), ВВП, ВВ (заряд у л)
- **Модель** — випадаючий список конкретних моделей з номенклатури залежно
  від обраного типу (напр. ВП-5, ВВК-3.5) — ємність підставляється
  автоматично з моделі, вільно ввести довільне число вже не можна

**Правила прив'язки:**
- Кабінет з комп'ютерною технікою → рівно одна прив'язка до кабінету, тип
  завжди **ВВК** (фіксовано, не змінюється)
- Загальна площа поверху (звичайні приміщення) → прив'язка до поверху, тип —
  один з дозволених у **Налаштуваннях** (⚙ на головному екрані), за
  замовчуванням лише **ВП**

**Де додавати:** з головного екрана (розділ "Вогнегасники" і кнопка знизу) —
майстер запитає будівлю → поверх → куди прив'язати (загальна площа чи
конкретний кабінет з ПК) → далі форма з полями. Той самий екран доступний і
з конкретного кабінету/поверху (іконка 🔥 на екрані поверху) — відкриється
одразу відфільтрованим на цей кабінет чи поверх.

**Фільтри:** на екрані "Вогнегасники" — випадаючі списки (управління →
будівля → поверх → кабінет), кожен звужує список нижче. На "Статистиці" —
управління → будівля → поверх, і додатково фільтр щитів за конкретною
територією, якщо їх декілька.

**Недостача:** "Статистика" (іконка 📊 на головній сторінці або на екрані
управління/будівлі/поверху) показує:
- скільки літрів вогнегасної речовини бракує по кожному поверху і сумарно
  (норма мінус сума ємностей зареєстрованих вогнегасників загальної площі)
- скільки кабінетів з ПК ще не мають призначеного вогнегасника ВВК

## 11. Управління, підтвердження видалення, Статистика/CSV/PDF

**Ієрархія:** з версії 2.4 над будівлями і територіями є ще один рівень —
**Управління**. Головний екран застосунку — список управлінь. Заходиш у
конкретне управління → бачиш його будівлі, території (ТВУЗ) і зведену
кількість вогнегасників. Будівлі рахують вогнегасники, території — щити;
обидва належать одному управлінню, але не пов'язані одне з одним напряму.
Управління й будівлю можна перейменувати (олівець у списку) в будь-який час.

При оновленні зі старішої версії всі наявні будівлі/території автоматично
потрапляють у створене управління-заглушку "Без управління" — дані не
губляться.

**Підтвердження видалення:** будь-яке видалення (управління, будівля,
поверх, кабінет, територія, вогнегасник) тепер питає "Ви дійсно хочете
видалити...?" перед виконанням.

**Статистика на кожному рівні:** екран "Статистика" (розрахунок недостачі +
CSV + PDF) доступний з кількох місць — з головної сторінки (без фільтра —
по всіх управліннях одразу), з екрана управління, будівлі й поверху, кожен
раз відфільтрований на свій рівень. Це один і той самий екран — просто з
різним початковим фільтром (Управління/Будівля/Поверх, без окремого
фільтра по кабінету — статистика поверху вже включає всі його кабінети).
Екран "Вогнегасники" лишився чистим списком-редактором конкретних записів,
без CSV/PDF — не всі об'єкти (напр. території) мають вогнегасники, тож
звітність винесена окремо.

**Формат CSV (з версії 2.7):** один файл, повне дерево даних — колонка
"Тип рядка" визначає, що описує рядок:
- **Вогнегасник** — конкретний вогнегасник, разом з управлінням/будівлею/
  поверхом (+площа поверху) і, якщо прив'язаний до кабінету, кабінетом
  (+площа, ознака ПК).
- **Поверх** — рядок-заглушка для поверху без жодного вогнегасника на
  загальній площі, щоб площа поверху не губилась.
- **Кабінет** — рядок-заглушка для кожного кабінету без власних
  вогнегасників (включно з кабінетами без ПК).
- **Територія** — управління, назва території, площа (щити).

Файл починається з UTF-8 BOM-маркера — тому коректно відкривається і в
Excel на Windows, і в WPS Office, і на Android (раніше без BOM Excel
показував кракозябри замість кирилиці, хоч WPS відкривав нормально).

**Експорт CSV:** іконка 📤 на екрані "Статистика". Питає назву файлу (за
замовчуванням показує рівень фільтра), формує CSV **саме за поточним
фільтром** (нічого не обрано = по всіх управліннях) і відкриває системне
меню "Поділитися".

**Імпорт CSV:** іконка 📥 поруч. Відкриває системний провідник файлів,
читає обраний `.csv` і створює або оновлює об'єкти:
- **Управління/будівля/поверх/кабінет/територія** — знаходяться за назвою
  або створюються автоматично, якщо їх ще немає. Нічого не має існувати
  заздалегідь — з версії 2.7 імпорт відновлює структуру повністю, включно
  з площами поверхів і кабінетів.
- Якщо об'єкт з такою назвою вже є — його площа (і ознака ПК для кабінету)
  **оновлюється** значенням з файлу (джерело правди — файл, що
  імпортується; так і працює синхронізація між пристроями).
- **Вогнегасники дедуплікуються** за інвентарним номером у межах
  кабінету/поверху — повторний імпорт того самого файлу оновлює наявні
  записи, а не плодить дублікати.
- Це водночас і механізм **бекапу/передачі даних**: та сама кнопка
  "Поділитися" при експорті годиться, щоб переслати повну базу (з нуля, на
  чистий пристрій) — там просто імпортують файл, і все дерево
  відновлюється.

**Експорт PDF:** іконка 📄 поруч. Формує друковану версію того самого
зведеного звіту (недостача, розбивка по поверхах, території/щити) для
офіційної звітності й ділиться нею так само через системне меню.

## 12. Редагування, номенклатура вогнегасників, довідка на сторінках

**Редагування — скрізь, де є об'єкт:**
- Управління, будівля — олівець у списку → діалог перейменування.
- Поверх, кабінет, територія, вогнегасник — повноцінна форма редагування
  (відкривається тапом по запису або олівцем).
- Додана модель у номенклатурі — видалення з підтвердженням; редагування —
  видалити й додати заново з новими параметрами.

**Номенклатура вогнегасників** (Налаштування → Номенклатура вогнегасників):
- Базові 30 моделей (описані в розділі 10 і на самій сторінці) — незмінні,
  без кнопки видалення.
- Кнопкою "+" можна додати свою модель понад базові: тип, код, ємність,
  категорія (переносний/пересувний). Код не може повторювати вже наявний
  (базовий чи доданий) у межах того самого типу.
- Додані моделі можна видалити (кошик, з підтвердженням) — після цього вони
  зникають з випадаючого списку при додаванні вогнегасника.
- Список моделей у формі вогнегасника і колонка "Модель" у CSV враховують
  і базові, і додані моделі.

**Довідка на кожній сторінці:** іконка "?" у верхньому куті кожного екрана
відкриває короткий опис — що на сторінці і що можна робити. Текст довідки
веде себе поруч із кодом кожного екрана (`PageHelpAction` у
`lib/widgets/page_help.dart`) — коли міняється функціонал сторінки, текст
довідки оновлюється разом з ним.

## 13. Логіка розрахунку норм (коротко)

Файл: `lib/services/calculation_service.dart`

- **Звичайні приміщення**: 1 літр вогнегасної речовини на кожні 10 м²
  (рахується сумарно по поверху, за вирахуванням площі кабінетів з ПК)
- **Кабінети з комп'ютерною технікою**: окремий вогнегасник по кожному
  кабінету — до 20 м² один клас, понад 20 м² більший клас
- **Територія (ТВУЗ)**: 1 пожежний щит на кожні 5000 м²
- Округлення завжди в більшу сторону (запас, не дефіцит)

⚠️ Точні класи/маси вогнегасників позначені `TODO` в коді — зафіксовані зі
слів замовника, без звірки з конкретним пунктом наказу. Якщо знайдеш точний
номер наказу — онови константи в `FireSafetyNorms`.
